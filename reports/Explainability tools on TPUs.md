# Captum on TorchTPU: an open, untested gap

**No mainstream PyTorch explainability library supports TPUs today, and no one appears to have built Captum on TorchTPU.** Across Captum, SHAP, TransformerLens, nnsight, Inseq, pyvene and pytorch-grad-cam, a clone-level grep found zero TPU, XLA, torch_xla or torch_tpu references in code, tests or CI, and issue searches turned up only two TPU-related items (a SHAP Kaggle install failure and a TransformerLens einsum numerics warning) ([Captum](https://github.com/meta-pytorch/captum), [SHAP #3926](https://github.com/shap/shap/issues/3926), [TransformerLens #591](https://github.com/TransformerLensOrg/TransformerLens/issues/591)). The JAX side has a thin native stack (Penzai, Mishax, Flax NNX capture/perturb) that runs on TPU because JAX does, but none of it documents TPU-specific interpretability support, and Penzai was archived in August 2026 ([Penzai](https://github.com/google-deepmind/penzai)). Timing matters: PyTorch/XLA is deprecated and will be archived on Nov 15, 2026, with TorchTPU as the replacement ([Google Cloud docs](https://docs.cloud.google.com/tpu/docs/pytorch-pods)), so no library will ever get XLA-specific work. TorchTPU supports about 450 ATen ops with forward and backward passes, and a device-generic autograd test suite was enabled on Oct 27, 2026 ([TorchTPU blog](https://pytorch.org/blog/introducing-torchtpu/), [PR 5887](https://github.com/google-pytorch/torch_tpu/pull/5887)). Whether the hooks and `torch.autograd.grad` paths Captum relies on work is undocumented and has not been tested by anyone in this research. The "no prior art" conclusion is strong for GitHub, arXiv and discuss.pytorch.org but weak for blogs, notebooks, Stack Overflow and Reddit, which were not searched effectively.

## Coverage limits that bound every claim here

This synthesis rests on four sets of notes with real methodological limits. Several researchers had no web search tool. The library-support and prior-art notes used the unauthenticated GitHub search API (which hit its rate limit partway through), local greps of shallow clones, the arXiv API and discuss.pytorch.org search. The JAX note had only page fetches, summarized by a small model, so dates and counts there are second-hand and several guessed URLs returned 404. Stack Overflow, Reddit, Medium, dev.to, Kaggle and Colab notebooks, GitHub Discussions and GitHub code search were not covered, so forks, gists and notebooks that import Captum under torch_xla would not show up. Three further limits shape how far the conclusions go:

1. **Nothing was run on a TPU.** Every "what breaks" statement below comes from reading library source or TorchTPU docs, not from observed failures. Hook and `.item()` counts are rough greps that include some utility and test-adjacent code.
2. **Hook and `torch.autograd.grad` support on TorchTPU is undocumented.** The TorchTPU docs say nothing explicit about module hooks, `torch.autograd.grad`, `create_graph`, `retain_graph`, `torch.func`, custom `autograd.Function` or CPU fallback for unsupported ops ([Feature set](https://torchtpu.readthedocs.io/en/latest/feature_set/), [public APIs](https://github.com/google-pytorch/torch_tpu/blob/main/docs/public_apis.md)). The contents of the autograd test list in PR 5887 were not read, so it is unknown whether hook or double-backward tests are included.
3. **Colab TPU support for TorchTPU is unconfirmed.** The feature-set page lists "Colab" as supported and the intro page has an Open-in-Colab badge, but the notebook needs sign-in, no install cell or torch version was seen, and the Colab TPU hardware generation is unknown ([Feature set](https://torchtpu.readthedocs.io/en/latest/feature_set/), [Intro](https://torchtpu.readthedocs.io/en/latest/intro_to_torchtpu/)). A Kaggle install attempt (issue 3047) was closed by a stale bot with no official route delivered ([Issue 3047](https://github.com/google-pytorch/torch_tpu/issues/3047)).

The PyTorch/XLA deprecation date was not independently re-verified by the researchers; it comes from the assignment brief and the Google Cloud docs page cited above, which the requester confirms.

## Seven PyTorch libraries, zero TPU support, one real warning

The seven libraries are healthy but TPU-blind. Captum (v0.9.0, last commit 2026-10-15, about 355k downloads a month) has CI jobs only for CPU and GPU, and its issue and PR searches for tpu, xla, torch_xla and torch_tpu all returned zero ([GitHub API](https://api.github.com/repos/meta-pytorch/captum), [workflows](https://github.com/meta-pytorch/captum/tree/master/.github/workflows)). SHAP dominates adoption at about 8.76M downloads a month, but its two TPU hits are a Kaggle install failure (#3926, a maintainer called it a networking problem) and an unrelated GPU error, and its six XLA hits are old TensorFlow DeepExplainer issues ([SHAP #3926](https://github.com/shap/shap/issues/3926), [pypistats](https://pypistats.org/api/packages/shap/recent)). nnsight's single "xla" hit (#532) was a Colab crash on CPU and T4 caused by a pinned dev version, not a TPU problem ([nnsight #532](https://github.com/ndif-team/nnsight/issues/532)). pytorch-grad-cam lists "cpu, cuda, cuda:0, mps or hpu" as devices and no TPU ([README](https://github.com/jacobgil/pytorch-grad-cam)). Inseq wraps Captum and inherits its risks, and pyvene is the stalest (last release May 2025) ([Inseq](https://github.com/inseq-team/inseq), [pyvene](https://github.com/stanfordnlp/pyvene)). Maintenance varies sharply: TransformerLens (v4.3.0, Oct 2026) and nnsight (v0.8.1, Oct 2026) are active, while Inseq has about 410 downloads a month ([pypistats](https://pypistats.org/api/packages/inseq/recent)).

| Library | TPU/XLA evidence found | Main risk (code reading, not tested) |
|---|---|---|
| Captum | None in code, CI, issues | Layer forward hooks, `.item()` and `torch.unique` loops in `_utils/common.py` ([source](https://github.com/meta-pytorch/captum/blob/master/captum/_utils/common.py)) |
| SHAP | Kaggle TPU install failure only | DeepExplainer full backward hooks and gradient overrides; GradientExplainer per-sample `autograd.grad` loop with `.cpu().numpy()` ([deep_pytorch.py](https://github.com/shap/shap/blob/master/shap/explainers/_deep/deep_pytorch.py)) |
| TransformerLens | Einsum numerics issue #591 | Heavy hook and `.item()` use, growing-length generation shapes; `get_device()` never selects XLA ([devices.py](https://github.com/TransformerLensOrg/TransformerLens/blob/main/transformer_lens/utilities/devices.py)) |
| nnsight | None | Tracing and interleaving via hooks and tensor `register_hook` ([backward.py](https://github.com/ndif-team/nnsight/blob/main/src/nnsight/intervention/backward.py)) |
| Inseq | None | Inherits Captum; autoregressive loops; cuda/mps-only device checks ([torch_utils.py](https://github.com/inseq-team/inseq/blob/main/inseq/utils/torch_utils.py)) |
| pyvene | None | Forward-pre-hook interventions; few host syncs ([constants.py](https://github.com/stanfordnlp/pyvene/blob/main/pyvene/models/constants.py)) |
| pytorch-grad-cam | None | Hooks plus per-sample `.cpu().item()` in AblationCAM and ScoreCAM ([ablation_cam.py](https://github.com/jacobgil/pytorch-grad-cam/blob/master/pytorch_grad_cam/ablation_cam.py)) |

The only documented TPU-specific correctness warning is TransformerLens #591, cross-posted from pytorch/xla#7050. It reported that `torch.einsum` produced systematically different training dynamics on TPU than on CPU, MPS or CUDA. A maintainer suggested installing `opt_einsum` as the workaround, and TransformerLens changed no code ([TL #591](https://github.com/TransformerLensOrg/TransformerLens/issues/591), [pytorch/xla #7050](https://github.com/pytorch/xla/issues/7050)). That is an XLA-era report, and whether TorchTPU shares the behavior is unknown.

Why do the libraries not break outright? Hooks are plain Python callables on `nn.Module`, so the analysis suggests they should run under any backend that preserves eager semantics. The practical problems would be performance and recompilation: each `.item()`, `.cpu()` or `torch.unique` forces a sync, and varying shapes trigger recompiles. That is an inference. On this reading, SHAP's CPU/NumPy explainers (Tree, Kernel, Permutation, Partition) are device-agnostic and pyvene is lowest risk, while ScoreCAM, AblationCAM and Captum's Occlusion, FeatureAblation and Shapley sampling are highest risk for performance. A zero-hit record in six of seven repos shows low demand, and does not show that TPU use went smoothly. Even the one prior Captum accelerator-friction precedent, an MPS Integrated Gradients error (#1240), was only checked by title ([Captum #1240](https://github.com/meta-pytorch/captum/issues/1240)).

## TorchTPU's autograd is real but the hooks story is a blank

TorchTPU's strongest signal is that backward passes are first-class: the blog claims forward and backward for all Core ATen ops needed by major architectures, and PR #5887 enabled device-generic `test_autograd` with 90 passing tests ([TorchTPU blog](https://pytorch.org/blog/introducing-torchtpu/), [PR 5887](https://github.com/google-pytorch/torch_tpu/pull/5887)). The exclusions in that PR are telling: an `index_reduce` lowering crash, `resize_` bumping the version counter twice, device memory stats after a failed backward, missing `triu_indices` and `median`, and complex128 `fill_`. Hooks do run in at least one real TorchTPU use: FSDP2 injects collectives through module hooks, and issue #5830 shows `fully_shard` working, though the blog notes that hooks break `torch.compile` into per-op dispatches ([TorchTPU blog](https://pytorch.org/blog/introducing-torchtpu/)). A closed PR also mentions forward pre-hooks counting Gemma4 checkpoint recomputes ([PR 4682](https://github.com/google-pytorch/torch_tpu/pull/4682), title only). The reasonable working hypothesis is that Python-level forward hooks, full backward hooks, `Tensor.register_hook` and custom `autograd.Function` work in eager mode, because the autograd engine is PyTorch's own. No source confirms it, and a smoke test is the first thing any project would need.

Known issues are specific enough to plan around. Issue #4409 (open) reports that backward of a `torch.compile(backend="tpu")` function whose inputs are views of a `requires_grad` tensor fails with `RuntimeProgramInputMismatch`, reproduced on v6e-8 and v5e with torch_tpu 0.2.0. This is a direct risk for per-sample attribution done by slicing a batch, with workarounds of passing the base tensor, cloning views or compiling the whole forward-plus-backward step ([Issue 4409](https://github.com/google-pytorch/torch_tpu/issues/4409)). Other open items include BatchNorm not updating running statistics in training mode (#5667), `leaky_relu` backward returning the full gradient at zero (#5961), and missing ops such as `linalg_cross` (#6070), `gcd` (#5725) and `_int_mm` (#5826) ([issues](https://github.com/google-pytorch/torch_tpu/issues?q=autograd+OR+hook+OR+captum+OR+torch.func+OR+colab), [#5961](https://github.com/google-pytorch/torch_tpu/issues/5961), [#6070](https://github.com/google-pytorch/torch_tpu/issues/6070)). Closed issue #4141 shows a silent failure type that matters for attribution: `avg_pool1d` returned a tensor outside the autograd graph, which would produce wrong or empty gradients without an error ([Issue 4141](https://github.com/google-pytorch/torch_tpu/issues/4141)). PR #5953 fixed it and #6050 adds gradient checks ([PR 5953](https://github.com/google-pytorch/torch_tpu/issues?q=autograd+OR+hook+OR+captum+OR+torch.func+OR+colab)).

The execution and shape model determines how Captum-style loops would behave. Data-dependent shapes such as `masked_select` force a blocking sync, and `torch.nonzero` is unsupported under compile ([Execution model](https://torchtpu.readthedocs.io/en/latest/torchtpu_execution_model/), [Dynamic shapes](https://torchtpu.readthedocs.io/en/latest/dynamic_shapes/)). Dynamic shapes are "bounded dynamism" with `mark_dynamic`, a default bucket size of 128 and at most 8 buckets, and `dynamic=True` is unsupported. The docs conflict on the default: the intro page says `dynamic=False` is the default and `None`/`True` are not production-ready, while the dynamic-shapes page presents `None` as the default ([Intro](https://torchtpu.readthedocs.io/en/latest/intro_to_torchtpu/)). Writes to broadcast results "always fail explicitly" and views are not free ([Memory model](https://torchtpu.readthedocs.io/en/latest/torchtpu_memory_model/)). Attribution loops that vary batch size or perturbation count, as in SHAP, LIME and occlusion, would recompile per shape unless padded or bucketed (inference). `torch.func`, vmap, higher-order gradients with `create_graph=True`, and CPU fallback for unsupported ops are all undocumented. The `TORCH_TPU_TIER3_COMPILATION_CACHE_ROOT` setting can persist compiled programs to a `gs://` path or filesystem, which the blog says is useful in Colab-like environments, and that would soften repeated-shape cost ([API reference](https://torchtpu.readthedocs.io/en/latest/api_reference/)).

## The JAX alternative covers mechanistic work but not attribution

JAX has the structural advantage of no hooks: Flax NNX offers `Module.sow`, `nnx.capture` and `nnx.Perturbation`/`perturb` for gradients with respect to intermediates, and `perturb` needs the perturbation tree initialized with the same batch structure under `vmap` ([Flax NNX guide](https://flax.readthedocs.io/en/latest/guides/extracting_intermediates.html)). DeepMind's Penzai (pytree selection and patching, Treescope visualization) was archived read-only on Aug 25, 2026 with no named successor, and Mishax (`ast_patcher`, `safe_greenlet`) has no releases and unclear maintenance ([Penzai](https://github.com/google-deepmind/penzai), [Mishax](https://github.com/google-deepmind/mishax)). The official `gemma` JAX library runs on CPU, GPU and TPU but does not advertise activation capture ([gemma](https://github.com/google-deepmind/gemma)). Google's PAIR saliency library (IG, XRAI, SmoothGrad, Grad-CAM) is framework-agnostic at its core with TF and PyTorch examples, and neither JAX nor TPU is mentioned. LIT is framework-agnostic with no TPU mention. Lucid is archived and tf-explain pins TensorFlow 2.6 ([saliency](https://github.com/PAIR-code/saliency), [LIT](https://github.com/PAIR-code/lit), [Lucid](https://github.com/tensorflow/lucid), [tf-explain](https://github.com/sicara/tf-explain)). The largest open interpretability effort, Gemma Scope 2 (published Dec 19, 2025, Gemma 3 270M to 27B, about 110 PB stored and over 1 trillion SAE parameters), never states its hardware ([DeepMind blog](https://deepmind.google/blog/gemma-scope-2-helping-the-ai-safety-community-deepen-understanding-of-complex-language-model-behavior/)). Its tutorial offers both JAX and PyTorch JumpReLU SAE implementations and points to SAELens (PyTorch) for loading ([HF gemma-scope](https://huggingface.co/google/gemma-scope)). That training used TPUs is plausible but unconfirmed. One JAX correctness warning is worth carrying: issue #41791 reports silent BF16 gather corruption involving a debug callback on libtpu 0.0.48, from a single report whose thread was not read ([JAX issues](https://github.com/google/jax/issues?q=TPU+hooks+OR+gradients+OR+attribution)). Community JAX SAE trainers and TransformerLens-style JAX ports were not surveyed, so the claim that JAX has no Captum or Inseq equivalent is limited to what these fetches could see.

## What a Captum port would fill, and what prior art exists

The clearest gap is a PyTorch-native, tested attribution path on the new official PyTorch TPU backend. The only TPU-plus-XAI prior art is hardware-acceleration research: arXiv 2103.11927 (2021, about 25x faster classification and 13x faster interpretation using a convolution/Fourier relationship), arXiv 2305.04887 (2023, claimed 39x time and 69x energy gains, with text overlap noted against the earlier paper and unclear whether real TPUs were used) and ApproXAI (arXiv 2504.17929, 2025, mapping integrated gradients, distillation and Shapley analysis to approximate matrix ops on TPU-based edge devices) ([2103.11927](https://export.arxiv.org/api/query?search_query=all:explainable+AND+all:TPU&max_results=15), [2305.04887](https://arxiv.org/abs/2305.04887), [2504.17929](https://arxiv.org/abs/2504.17929)). Only abstracts were read, and their speedups are authors' claims on their own frameworks, not comparable to a Captum run. None is a drop-in PyTorch workflow. Searches for `captum tpu`, `captum xla`, `integrated gradients tpu`, `torch_tpu captum`, `torchtpu explainability` and `TorchTPUSprint` returned zero repositories, and `repo:meta-pytorch/captum TPU` and `repo:pytorch/xla captum` returned zero issues and PRs ([GitHub search](https://api.github.com/search/repositories?q=captum+tpu), [issues](https://api.github.com/search/issues?q=repo:meta-pytorch/captum+TPU&per_page=10)). discuss.pytorch.org queries were also empty, and its TPU category holds only two topics, one announcing TorchTPU DevLabs for Nov 9-10, 2026 ([forum](https://discuss.pytorch.org/c/tpu/45)). The existing TorchTPU community repos (vllm-torchtpu, sglang-torchtpu, a RAG benchmark, a Gemma 4 serving/QAT repo, nanochat and verl ports) all target serving, training or benchmarks ([GitHub search](https://api.github.com/search/repositories?q=torchtpu)). No #TorchTPUSprint entries or announcement were found, probably because they are not indexed on GitHub. TorchTPU is active (v0.2.0, about 802 stars, 244 open PRs) but its docs list ecosystem partners (Hugging Face, Ray, vLLM, SGLang, TorchTitan, TorchRec, llm-d) with nothing on interpretability ([torch_tpu](https://github.com/google-pytorch/torch_tpu), [Google Cloud](https://docs.cloud.google.com/tpu/docs/pytorch-on-tpu)).

The performance case is plausible but not benchmarked. Integrated Gradients defaults to `n_steps=50` and evaluates `n_steps` times the number of examples, in one batch unless `internal_batch_size` is set ([Captum docs](https://captum.ai/api/integrated_gradients.html)). Users repeatedly hit memory limits: GradientShap needs an `internal_batch_size` argument (#1350, open) and LLM attribution memory use on Llama2 is a recurring question (#1430) ([#1350](https://github.com/meta-pytorch/captum/issues/1350), [#1430](https://github.com/meta-pytorch/captum/issues/1430)). Such workloads are batchable and matmul-dominated, which fits TPU throughput (inference), and no concrete GPU or CPU timing baseline was retrieved. The Vertex AI Explainable AI page was not read and could show how Google runs IG, XRAI and sampled Shapley in production ([Vertex AI](https://docs.cloud.google.com/vertex-ai/docs/explainable-ai/overview)).

A project could therefore fill four gaps, each with uneven evidence. The first is verification: a smoke-test matrix of forward and backward hooks, `autograd.grad` with and without `create_graph`, custom `autograd.Function` and `torch.func` on TorchTPU, which the docs leave blank and which would also exercise TorchTPU's still-open gradient bugs. The second is Captum patches for XLA-style execution: replacing `.item()` and `torch.unique` loops, padding or bucketing perturbation batches to fit bounded dynamism, and avoiding view inputs under compile per #4409. The third is device handling, since TransformerLens, Inseq and pytorch-grad-cam enumerate only cuda, mps, cpu or hpu. The fourth is documented guidance and CI: Captum has no accelerator job beyond CPU and GPU, and the TransformerLens einsum warning should be re-checked on TorchTPU. Scope matters because the user-facing story depends on Colab TPU access, which is unconfirmed, and on TPU VMs (v5e, v5p, v6e, v7) that are not free ([FAQ](https://torchtpu.readthedocs.io/en/latest/faq/)). Also unresolved are Python version (3.12 in the VM guide, 3.11+ in the README) and the torch version range ([VM guide](https://torchtpu.readthedocs.io/en/latest/get_started_on_a_vm/), [README](https://github.com/google-pytorch/torch_tpu)).

## Conclusion

The central finding is an absence on both sides. The libraries do not mention TPUs, and TorchTPU's docs do not mention the libraries, so the compatibility question lives entirely in generic PyTorch behavior that neither team has published results on. The deprecation of PyTorch/XLA changes the calculus: upstream XLA work is a dead end, so compatibility will hinge on whether TorchTPU's eager mode faithfully preserves hook and autograd semantics, and a Captum port would double as an independent correctness test of that. The most credible first deliverable is a small reproducible test suite plus a few Captum fixes, not a full port.

Two cautions should temper enthusiasm. The "nobody has done it" claim means "no prior art found in GitHub, arXiv and PyTorch forum searches", and it could be overturned by a notebook or blog the researchers could not reach. The bigger risks (silent no-gradient bugs like #4141, compile-time view failures like #4409, recompilation under varying perturbation counts) are plausible but unobserved here, so the first experiment should be to run Captum's Integrated Gradients and Layer Grad-CAM on a small model on a TorchTPU v6e VM and record what actually happens before committing to scope.
