# TPU/XLA support status of PyTorch explainability and interpretability libraries (as of 30 Oct 2026)

Method note: GitHub unauthenticated search API (issues/PRs) plus shallow clones of each default branch (HEAD dated Aug-Oct 2026, except pyvene Mar 2026), grepped locally for `tpu`, `torch_xla`, `xla`, `torch_tpu` (the code search API needs auth, so local grep replaced it). Clone grep is the strongest evidence for code/docs/tests/CI. Hook and `.item()` counts are rough greps excluding tests/docs.

## Does each library mention TPU / XLA / torch_xla / torch_tpu (README, docs, code, tests, CI, issues, PRs)?

### Takeaway
None of the seven libraries has any TPU/XLA/torch_xla/torch_tpu support, code path, test or CI job. The only TPU-related hits across all repos are two issues (shap #3926 Kaggle TPU install problem; TransformerLens #591 einsum numerics on TPU) and an nnsight Colab crash that was not TPU-related. No library mentions torch_tpu/TorchTPU.

### Inferences
- Any TPU use of these libraries is unsupported and untested upstream; users would be on their own. Since XLA is being archived, upstream XLA-specific work is unlikely; compatibility would hinge on whether TorchTPU handles generic eager PyTorch (hooks, autograd) transparently, which is outside these notes.
- The only documented TPU-specific correctness warning in this set is TransformerLens/einsum.

## Core mechanisms each library depends on that are risky on TPU

### Takeaway
All rely on PyTorch module hooks and eager autograd, which are only weakly compatible with XLA's lazy/graph model. The riskiest are SHAP DeepExplainer (full backward hooks plus in-place gradient overrides), pytorch-grad-cam (hooks plus `.cpu().item()` in loops), Captum (heavy hooks, `.item()` and `torch.unique` data-dependent shapes), and nnsight (tracing/interleaving built on hooks and Python frame tricks). These are my code-reading inferences, not tested failures.

### Cited Findings
- Rough non-test grep counts of `register_forward(_pre)_hook` / backward-hook or tensor `register_hook` / `autograd.grad` or `.backward()` / `.item()` / hardcoded cuda / `nonzero|unique|masked_select`: TransformerLens 28/8/22/153/18/10; Captum 23/19/18/14/0/6; Inseq 5/0/1/13/4/7; nnsight 0/2/16/2/1/0; pytorch-grad-cam 3/1/8/4/1/0; pyvene 2/0/1/4/0/2; SHAP 3/1/4/3/2/8. (Own grep of clones; approximate, includes some library-internal and docs-like code.)
- Captum registers forward hooks on layers for layer attribution (`captum/_utils/gradient.py`, `register_forward_hook` at ~line 366), and `_utils/common.py` calls `target.item()` and `torch.max(mask).item()`, and loops `for feature_idx in torch.unique(mask)` with `.item()` per element (lines ~665, 940, 952-953). These are device-sync and dynamic-shape patterns. Captum mostly uses `device=inp.device`, i.e. device-agnostic placement; zero hardcoded cuda in non-test code. — [gradient.py](https://github.com/meta-pytorch/captum/blob/master/captum/_utils/gradient.py), [common.py](https://github.com/meta-pytorch/captum/blob/master/captum/_utils/common.py)
- SHAP DeepExplainer (PyTorch) installs `register_forward_hook` and `register_full_backward_hook` on every module and overrides gradients (DeepLIFT rules), then calls `torch.autograd.grad`. GradientExplainer calls `torch.autograd.grad(..., retain_graph=...)` in a per-sample loop, adds forward hooks for interim layers and does `.cpu().numpy()` each iteration. Device is taken from inputs (`device=X[t].device`). — [deep_pytorch.py](https://github.com/shap/shap/blob/master/shap/explainers/_deep/deep_pytorch.py), [_gradient.py](https://github.com/shap/shap/blob/master/shap/explainers/_gradient.py)
- Most of SHAP's popular explainers (Tree, Kernel, Permutation, Partition) are CPU/NumPy-based and do not use PyTorch devices, so they are device-agnostic by default (own reading; not a TPU claim).
- pytorch-grad-cam: `ActivationsAndGradients` registers forward hooks and a tensor `register_hook` to capture gradients; AblationCAM/ScoreCAM call `target(o).cpu().item()` per ablated sample (host sync in loops); GuidedBackpropReLU and ShapleyCAM use custom autograd functions / Hessian-vector products. — [activations_and_gradients.py](https://github.com/jacobgil/pytorch-grad-cam/blob/master/pytorch_grad_cam/activations_and_gradients.py), [ablation_cam.py](https://github.com/jacobgil/pytorch-grad-cam/blob/master/pytorch_grad_cam/ablation_cam.py), [score_cam.py](https://github.com/jacobgil/pytorch-grad-cam/blob/master/pytorch_grad_cam/score_cam.py)
- nnsight: dependencies are torch, greenlet, pydantic, cloudpickle, transformers, with accelerate-hook handling; it intercepts module execution by interleaving/tracing, uses tensor `register_hook` for backward (`intervention/backward.py`), and caches tensors off the compute device (`cache.py` default device cpu). Its source wrapper re-applies accelerate's device-alignment hooks. This sophisticated interleaving was not designed with XLA lazy tensors in mind (inference). — [pyproject.toml](https://github.com/ndif-team/nnsight/blob/main/pyproject.toml), [source.py](https://github.com/ndif-team/nnsight/blob/main/src/nnsight/intervention/source.py), [backward.py](https://github.com/ndif-team/nnsight/blob/main/src/nnsight/intervention/backward.py)
- TransformerLens: ~16 `einsum` uses (documented TPU numerics problem, #591); 153 `.item()` hits (many in tests/utilities but counted loosely); hooks via its own `HookPoint` wrapper modules; hardcoded device strings and cuda-specific code in some paths (18 hits), though `get_device()` is cuda/mps/cpu only. Generation and KV-cache paths use dynamic shapes (growing sequence length), which cause XLA recompilation (inference). — [TL #591](https://github.com/TransformerLensOrg/TransformerLens/issues/591)
- Inseq: attribution methods wrap Captum (feature attribution via Captum), so it inherits Captum's risks; adds `torch.backends.cuda.is_built` / `mps` device checks in `utils/torch_utils.py` and autoregressive generation loops. No TPU device option. — [torch_utils.py](https://github.com/inseq-team/inseq/blob/main/inseq/utils/torch_utils.py)
- pyvene: interventions implemented through `register_forward_pre_hook` / forward hooks (constant `CONST_INPUT_HOOK = "register_forward_pre_hook"`), explicit `intervenable.set_device(...)`; hardcoded `"cuda"` only in tutorial code, not the core library. Few `.item()` calls, so mostly hook-risk. — [constants.py](https://github.com/stanfordnlp/pyvene/blob/main/pyvene/models/constants.py)

### Inferences
- Hooks themselves are plain Python callables on `nn.Module` and should run under XLA in eager-looking mode (tracing recorded into the lazy graph); the bigger practical issues would be (a) every `.item()`/`.cpu()`/`torch.unique` forcing graph materialization and recompiles, (b) data-dependent shapes, (c) varying shapes recompiling, (d) numerics differences (einsum) and (e) in-place gradient overrides and `retain_graph` loops being slow. This is analysis, not tested.
- Least risky: SHAP's non-deep explainers (CPU), pyvene (few syncs), Captum attribution methods on small models. Most risky for performance: ScoreCAM/AblationCAM and Captum Occlusion/FeatureAblation/Shapley (per-sample loops with syncs), nnsight and TransformerLens for generation workflows.

### Gaps
- No empirical TPU/TorchTPU runs; the effect of TorchTPU's hook/autograd handling is unknown to me.
- TransformerLens `.item()` and hardcoded-cuda counts include some utility/test-adjacent code; real hot-path count is unknown.
